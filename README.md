# sql_diff.py

Сравнивает два mysqldump-файла одной и той же базы данных и формирует SQL-скрипт, который приводит вторую базу в соответствие с первой.

Требуется Python 3.8+. Внешних зависимостей нет, используется только стандартная библиотека.

## Сравнение данных

Строки сопоставляются по первичному ключу таблицы:

* строка есть в основном дампе, но отсутствует во втором: `INSERT`;
* строка есть в обоих дампах, но значения различаются: `UPDATE`, в `SET` попадают только изменившиеся колонки;
* строка есть только во втором дампе: игнорируется, `DELETE` не формируются.

Вывод состоит из отдельных команд `INSERT INTO t (cols) VALUES (...)` и `UPDATE t SET ... WHERE pk = ...`. `INSERT ... ON DUPLICATE KEY UPDATE` не используется.

Схемы сопоставляются по именам колонок, поэтому дампы могут немного отличаться структурой. Если у таблицы нет первичного ключа или его колонок нет во втором дампе, сравнение идет по полному кортежу общих колонок, дубликаты при этом не теряются. `UPDATE` для таких таблиц не формируется.

## Достройка схемы

Если в основном дампе есть объекты схемы, которых нет во втором:

* таблица отсутствует целиком: в начало выходного файла добавляется полный `CREATE TABLE` из основного дампа вместе с `DROP TABLE IF EXISTS` перед ним;
* отсутствует колонка: перед данными таблицы добавляется `ALTER TABLE ... ADD COLUMN` с определением из основного дампа (тип, NOT NULL, DEFAULT, COMMENT, AUTO_INCREMENT);
* если новая колонка входит в первичный ключ, уникальный или обычный индекс, добавляются соответствующие `ADD PRIMARY KEY`, `ADD UNIQUE KEY`, `ADD KEY`. Индексы, уже существующие во втором дампе по имени, не дублируются. Если первичный ключ во второй таблице уже есть, а колонка входит в ключ основного дампа, команда не формируется, в отчет пишется предупреждение;
* если колонка участвует во внешнем ключе, добавляется `ADD CONSTRAINT ... FOREIGN KEY ...`.

После генерации `ALTER` колонка считается существующей и включается в `INSERT` и `UPDATE` на общих основаниях.

## Нормализация значений

Числа сравниваются как числа: `1` и `1.0` считаются равными, поэтому разное текстовое представление float в дампах не дает ложных `UPDATE`.

Переводы строк внутри строковых литералов (`\r\n`, `\n`, `\r`, включая удвоенные формы с экранированным backslash) вырезаются из выходного SQL и игнорируются при сравнении: если значения различаются только переводами строк, `UPDATE` не формируется. Числа, NULL и hex-литералы не затрагиваются.

## Запуск

```bash
python sql_diff.py <основной_дамп> <второй_дамп> [опции]
```

Примеры:

```bash
python sql_diff.py primary.sql secondary.sql -o output/diff.sql
python sql_diff.py primary.sql secondary.sql -e log_error,logmail
python sql_diff.py primary.sql secondary.sql -t admsettings,goods
python sql_diff.py primary.sql secondary.sql --report logs/report.txt
python sql_diff.py primary.sql secondary.sql --no-report
```

## Параметры

| Параметр | Описание |
|---|---|
| `primary` | путь к основному дампу, источник истины |
| `secondary` | путь ко второму дампу, база, которую приводим в соответствие |
| `-o, --output` | выходной SQL-файл, по умолчанию `output/diff.sql` |
| `-e, --exclude` | таблицы через запятую, которые полностью игнорировать |
| `-t, --tables` | обрабатывать только перечисленные таблицы |
| `--report` | путь к текстовому отчету, по умолчанию `output/report.txt` |
| `--no-report` | не писать отчет в файл, сводка выводится в stdout |

## Формат выходного файла

Кодировка UTF-8. В начале заголовок с датой, именами входных файлов и счетчиками, затем `SET NAMES utf8mb4;` и `SET FOREIGN_KEY_CHECKS=0;`. Далее:

1. секция DDL с `CREATE TABLE` отсутствующих таблиц, если такие есть;
2. по каждой таблице секция с числом команд: сначала `ALTER` недостающих колонок, затем `INSERT` и `UPDATE`;
3. в конце `SET FOREIGN_KEY_CHECKS=1;`.

## Ограничения

* Строковые литералы предполагаются в одинарных кавычках с backslash-экранированием, это стандарт mysqldump.
* Оба дампа загружаются в память целиком, для очень больших баз нужен соответствующий объем RAM.
* Таблицы второго дампа, отсутствующие в основном, не изменяются.
* Порядок применения DDL не оптимизируется по зависимостям таблиц, ссылочную целостность на время загрузки снимает `FOREIGN_KEY_CHECKS=0` в шапке файла.
